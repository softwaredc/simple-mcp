# 基准测试

以下所有数字都在下面描述的机器上、用 `go/cmd/mcpbench` 实测得出。
没有外推，也没有拿我没亲自跑过的数字来对比。英文版：[BENCHMARKS.md](BENCHMARKS.md)。

## 参考环境

```
go1.22.2 linux/amd64，16 核
Intel Core Ultra 7 356H（移动端，6P+8E+2LPE）
WSL2，内核 6.18.33，Ubuntu 24.04
gcc 13.3.0，g++ 13.3.0
```

WSL2 不是裸机。它的 futex 和系统调用开销比原生内核高，所以这里的绝对数字
比同一份代码在真实硬件上跑要差。但各传输方式之间的**比值**仍然成立。

复现方式：

```bash
make bench          # 或者：cd go && go run ./cmd/mcpbench -n 20000
```

## 先说运行间波动

同一个二进制连跑五次，stdio p50：

```
10,742   10,874   11,049   11,111   11,356 ns
```

同一段时间内是 6% 的离散度。但相隔几小时的两次运行之间，
同一个二进制给出过 8.9 µs 和 11.5 µs——25% 的差距。
原因是 CPU 频率缩放和机器上当时还跑着什么。

所以：下面的表是一次有代表性的运行。中位数稳定到可以引用，
尾延迟在两次运行之间能差一倍。报中位数，别信尾延迟，
拿它跟任何东西对比之前先重跑一遍。

## 往返延迟：一次 `tools/call`

20,000 次迭代，前面 1,000 次预热，分位数从完整样本集算出（不是分桶统计）。

| 传输                  | p50           | p90        | p99        | p99.9      |
| ------------------- | -------------:| ----------:| ----------:| ----------:|
| stdio               | **10,742 ns** | 20,991 ns  | 76,266 ns  | 276,777 ns |
| HTTP（Streamable，回环） | 59,610 ns     | 113,603 ns | 295,533 ns | 616,020 ns |

HTTP 大约是 stdio 的 5.5 倍。这不是 JSON 的锅——是系统调用、连接处理，
以及每次往返都是一次全新的 POST。

## 这 10.7 µs 花在哪

这部分才让头条数字有意义。

| 组成部分                  | 耗时       | 占比  |
| --------------------- | --------:| ---:|
| 一对请求/响应的 JSON 编码 + 解码 | 1,508 ns | 14% |
| 传输、协程交接、调度唤醒          | 9,234 ns | 86% |

JSON 那一半是单独测的：同一个请求解码、同一个响应编码，紧循环，
没有管道没有协程。剩下的是管道写入、channel 发送，
以及唤醒一个随后要被调度的线程。

两个结论。第一，换更快的 JSON 库最多让这个数字变动 14%，
所以优化 MCP 实现应该先看唤醒路径。第二，HTTP 那 5.5 倍是同一个故事的放大版：
**协议很便宜，系统调用不便宜。**

## 吞吐

| 传输    | 消息/秒   |
| ----- | ------:|
| stdio | 66,865 |
| HTTP  | 14,750 |

这里的吞吐指的是「一个客户端和一个服务端能多快交换 `tools/call` 往返」，
不是「环一次能吞多少消息」。批处理的流水线会给出另一个大得多的数字，
但 agent 不是那么干的。

## 报文大小

| 消息                    | 字节  |
| --------------------- | ---:|
| `initialize` 响应       | 205 |
| `tools/list` 响应，2 个工具 | 352 |
| `tools/call` 请求 + 响应  | 170 |

`tools/list` 是每个 agent 第一个发的消息，所以它的大小就是你在 trace 里
直接看到的成本。一个带十五个工具的真实服务端会到几千字节，
这正是 `nextCursor` 分页存在的原因。

## 这里没测什么

任何需要把模型放进来的东西：

- 模型选中正确工具的频率
- 改工具描述能不能提升调用准确率
- 某种上下文压缩策略能省多少

这些需要 LLM、评测集和预算。它们会单独报告，附上产出它们的测试装置，
或者根本不报。一个把协议成本和模型行为混在一起悄悄发布的基准，不是基准。
